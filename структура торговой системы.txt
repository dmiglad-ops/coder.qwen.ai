## 1. 📖 ОБЩЕЕ ОПИСАНИЕ

### 1.1. Назначение
Система автоматической торговли криптовалютами на бирже Bybit, использующая ансамбль специализированных ML-моделей (на базе Laya) для принятия торговых решений.

### 1.2. Ключевые характеристики
- **Биржа:** Bybit (demo account, 10,000$)
- **Торгуемые инструменты:** до 10 валютных пар одновременно
- **Таймфреймы:** 5m, 15m, 30m, 1h, 4h, 1d (стандартные Bybit)
- **Модель принятия решений:** иерархия из 4 специалистов + 1 Директор на каждую пару
- **Модель инференса:** Laya (421M параметров, дообученная на русском)

### 1.3. Ключевой принцип
**Разные пары — разные наборы специалистов.** Для каждой торговой пары может быть подключен свой уникальный набор советников с индивидуальными весами и настройками.

### 2.2. Концепция "Специалист → Пара"

**Критически важное решение:** Специалисты (советники) — это **переиспользуемые компоненты**, которые подключаются к конкретным торговым парам через конфигурацию.

```
┌──────────────────────────────────────────────────────┐
│              РЕЕСТР СПЕЦИАЛИСТОВ                     │
├──────────────────────────────────────────────────────┤
│  trend_v1     (обучен на BTC)     → работает на 4h   │
│  trend_v2     (обучен на ETH)     → работает на 1h   │
│  osc_v1       (обучен на всех)    → работает на 30m  │
│  volume_v1    (обучен на всех)    → работает на 5m   │
│  market_v1    (обучен на всех)    → работает на 1h   │
│  trend_alt_v1 (обучен на SOL)     → работает на 30m  │
└──────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────┐
│           ПРИВЯЗКА К ПАРОВЫМ КОНФИГУРАЦИЯМ           │
├──────────────────────────────────────────────────────┤
│  BTC_USDT:                                           │
│    trend:    trend_v1     (вес 0.30)                 │
│    osc:      osc_v1       (вес 0.25)                 │
│    volume:   volume_v1    (вес 0.25)                 │
│    market:   market_v1    (вес 0.20)                 │
│                                                      │
│  ETH_USDT:                                           │
│    trend:    trend_v2     (вес 0.35)                 │
│    osc:      osc_v1       (вес 0.25)                 │
│    volume:   volume_v1    (вес 0.20)                 │
│    market:   market_v1    (вес 0.20)                 │
│                                                      │
│  SOL_USDT:                                           │
│    trend:    trend_alt_v1 (вес 0.40)                 │
│    osc:      osc_v1       (вес 0.30)                 │
│    volume:   volume_v1    (вес 0.30)                 │
│    market:   market_v1    (вес 0.00) ← отключен!     │
└──────────────────────────────────────────────────────┘
```

**Принцип:**
- Один и тот же специалист (`osc_v1`) может использоваться на **нескольких парах** одновременно
- Один и тот же тип специалиста (например, "trend") может быть **разным специалистом** на разных парах
- Вес специалиста можно устанавливать **индивидуально для каждой пары** (включая 0 = отключен)

### 2.3. Директор для каждой пары

**Для каждой пары — свой Директор** (или общий Директор с контекстом пары):

```
Директор для BTC:
  - Получает решения от 4 специалистов, привязанных к BTC
  - Знает контекст пары (волатильность, объемы, режим)
  - Принимает финальное решение о сделке на BTC

Директор для ETH:
  - Получает решения от 4 специалистов, привязанных к ETH
  - Знает контекст пары
  - Принимает финальное решение о сделке на ETH
```

### 3.2. Схема SQLite базы (`metadata.db`)

```sql
-- Модели и их версии
CREATE TABLE models (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL,               -- trend_v1, osc_v1, director_btc
    model_type TEXT NOT NULL,         -- specialist / director
    specialist_category TEXT,         -- trend / oscillators / volume / market
    version TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    -- Метрики обучения
    train_sharpe REAL,
    train_max_drawdown REAL,
    train_win_rate REAL,
    train_profit_factor REAL,
    
    -- Метрики бэктеста (out-of-sample)
    backtest_sharpe REAL,
    backtest_max_drawdown REAL,
    backtest_win_rate REAL,
    backtest_profit_factor REAL,
    backtest_start_date DATE,
    backtest_end_date DATE,
    
    -- Метрики живой торговли
    live_sharpe REAL,
    live_max_drawdown REAL,
    live_win_rate REAL,
    live_profit_factor REAL,
    
    -- Конфигурация
    config_path TEXT,                 -- путь к YAML конфигу модели
    weights_path TEXT,                -- путь к файлам весов модели
    training_config TEXT,             -- JSON с параметрами обучения
    
    -- Композитный скор
    composite_score REAL,             -- вычисляется по формуле
    
    status TEXT DEFAULT 'active',     -- active / archived / deprecated
    notes TEXT
);

-- Привязка моделей к парам (кто работает на какой паре)
CREATE TABLE pair_assignments (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,             -- BTC_USDT
    specialist_category TEXT NOT NULL, -- trend / oscillators / volume / market
    model_id INTEGER NOT NULL,
    weight REAL DEFAULT 0.25,         -- вес в ансамбле (0 = отключен)
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    FOREIGN KEY (model_id) REFERENCES models(id),
    UNIQUE(symbol, specialist_category, model_id)
);

-- Торговые сделки (история)
CREATE TABLE trades (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    side TEXT NOT NULL,               -- long / short
    entry_price REAL,
    exit_price REAL,
    quantity REAL,
    entry_time TIMESTAMP,
    exit_time TIMESTAMP,
    pnl REAL,
    pnl_pct REAL,
    
    -- Кто принял решение
    director_model_id INTEGER,
    trend_confidence REAL,
    oscillators_confidence REAL,
    volume_confidence REAL,
    market_confidence REAL,
    
    -- Метаданные
    strategy TEXT,
    stop_loss_price REAL,
    take_profit_price REAL,
    commission REAL,
    
    FOREIGN KEY (director_model_id) REFERENCES models(id)
);

-- Открытые позиции
CREATE TABLE positions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    side TEXT NOT NULL,
    entry_price REAL,
    quantity REAL,
    entry_time TIMESTAMP,
    stop_loss_price REAL,
    take_profit_price REAL,
    current_pnl REAL,
    status TEXT DEFAULT 'open',       -- open / closed / stopped
    
    FOREIGN KEY (symbol) REFERENCES pair_assignments(symbol)
);

-- Результаты бэктестов
CREATE TABLE backtests (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    model_id INTEGER,
    symbol TEXT,
    start_date DATE,
    end_date DATE,
    initial_balance REAL,
    final_balance REAL,
    total_trades INTEGER,
    win_rate REAL,
    sharpe REAL,
    max_drawdown REAL,
    profit_factor REAL,
    sortino REAL,
    
    config_snapshot TEXT,             -- JSON конфига на момент бэктеста
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    
    FOREIGN KEY (model_id) REFERENCES models(id)
);

-- Системные события и логи
CREATE TABLE events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    level TEXT NOT NULL,              -- INFO / WARNING / ERROR / CRITICAL
    component TEXT,                   -- coordinator / trend_v1 / director_btc / executor
    event_type TEXT,                  -- trade_opened / error / model_loaded / alert_sent
    message TEXT,
    metadata TEXT                     -- JSON с доп. данными
);

-- Алерты
CREATE TABLE alerts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    timestamp TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    severity TEXT NOT NULL,           -- info / warning / critical
    channel TEXT,                     -- max_bot / telegram / email (заглушки)
    recipient TEXT,
    message TEXT,
    was_sent BOOLEAN DEFAULT FALSE,
    error_message TEXT
);
```

## 5. ⚙️ КОНФИГУРАЦИЯ

### 5.1. `config/system.yaml` — Общие настройки

```yaml
system:
  name: "Crypto Trading System"
  version: "1.0.0"
  log_level: "INFO"
  
  # Процессы
  processes:
```

## 6. 🔄 ПАЙПЛАЙН ДАННЫХ

### 6.1. Сбор исторических данных

```
1. Определяем список пар и таймфреймов из конфигурации
2. Для каждой пары и каждого таймфрейма:
   a. Проверяем, какие месяцы уже есть в Parquet
   b. Дозагружаем недостающие месяцы с Bybit
   c. Сохраняем в Parquet
3. Пересчитываем индикаторы для новых данных
4. Сохраняем индикаторы в Parquet
```

### 6.2. Реалтайм поток

```
1. Подключаемся к Bybit WebSocket для каждой пары
2. Получаем новые свечи в реалтайме
3. Обновляем индикаторы для последней свечи
4. Отправляем обновленные данные специалистам через ZeroMQ
5. Специалисты возвращают решения
6. Директор агрегирует решения
7. Executor исполняет сделку (если есть сигнал)
```

## 7. 🧠 ПРОЦЕСС ПРИНЯТИЯ РЕШЕНИЙ

### 7.1. Полный цикл (для каждой пары)

```
Шаг 1: Сбор данных
  └── Получаем свежие свечи со всех нужных таймфреймов
  └── Рассчитываем индикаторы

Шаг 2: Сериализация состояния
  └── Создаем состояние для каждого специалиста
  └── Формат: { "structured": {...}, "description": "..." }

Шаг 3: Параллельный вызов специалистов
  └── Отправляем состояние каждому специалисту через ZeroMQ
  └── Ждем ответы с таймаутом (5 сек)
  └── Если специалист не ответил → его вес = 0 на эту итерацию

Шаг 4: Агрегация Директором
  └── Директор получает все ответы
  └── Учитывает веса специалистов для этой пары
  └── Формирует финальное решение

Шаг 5: Риск-менеджмент
  └── Проверяем: не превышен ли дневной лимит убытков?
  └── Проверяем: не больше ли максимального числа позиций?
  └── Проверяем: достаточная ли уверенность?

Шаг 6: Исполнение
  └── Если все проверки пройдены → открываем позицию
  └── Устанавливаем стоп-лосс и тейк-профит
  └── Записываем сделку в базу
  └── Отправляем уведомление в МАКС (опционально)

Шаг 7: Мониторинг позиции
  └── Отслеживаем открытые позиции
  └── При срабатывании стоп/тейк → закрываем и логируем
```

## 8. 🎓 ОБУЧЕНИЕ МОДЕЛЕЙ

### 8.1. Подход

**Основной метод:** Out-of-sample
- **Обучение:** Данные 2022-2024
- **Тестирование:** Данные 2025-2026 (один раз, без повторного использования)

**Дополнительно:** Возможность ручного переобучения по запросу пользователя
- Пользователь может запустить переобучение через дашборд или скрипт
- При переобучении создается новая версия модели

### 8.2. Пайплайн обучения

```
1. Подготовка данных
   └── Загрузка исторических свечей (2022-2024)
   └── Расчет индикаторов
   └── Генерация меток (realized returns через N свечей)

2. Обучение специалиста
   └── Загрузка базовой Laya (laya-ru-tickets)
   └── Fine-tuning на данных специалиста
   └── Сохранение весов

3. Валидация
   └── Прогон на валидационной выборке (последние 10% тренировочных данных)
   └── Проверка калибровки вероятностей

4. Бэктест (out-of-sample)
   └── Прогон на тестовых данных (2025-2026)
   └── Расчет всех метрик
   └── Сравнение с предыдущей версией

5. Регистрация
   └── Если метрики лучше → регистрация новой версии в реестре
   └── Если хуже → отклонение и уведомление
```

### 8.3. Формула композитного скора

```python
def calculate_composite_score(metrics):
    """
    Вычисляет композитный скор модели.
    Чем выше скор, тем лучше модель.
    """
    # Нормализация метрик к [0, 1]
    pf_norm = min(metrics['profit_factor'] / 3.0, 1.0)  # PF 3.0 = максимум
    sharpe_norm = min(metrics['sharpe'] / 3.0, 1.0)     # Sharpe 3.0 = максимум
    dd_norm = 1.0 - min(metrics['max_drawdown'], 0.5)   # MaxDD 50% = минимум
    wr_norm = metrics['win_rate']                        # Уже в [0, 1]
    
    # Взвешенная сумма
    score = (
        0.35 * pf_norm +      # Profit Factor (самый важный)
        0.30 * sharpe_norm +   # Sharpe Ratio
        0.20 * dd_norm +       # 1 - Max Drawdown
        0.15 * wr_norm         # Win Rate
    )
    
    return score
```

## 10. 🛡️ ОБРАБОТКА ОШИБОК

### 10.1. ПРИНЦИП (ОБЯЗАТЕЛЬНО!)

**При любой поломке:**
1. ✅ **Уведомить пользователя** через МАКС бота
2. ❌ **НЕ закрывать позиции** автоматически
3. ❌ **НЕ открывать новые позиции**
4. ⏸️ Перевести систему в режим **"PAUSED"**
5. 👤 **Ждать ручного вмешательства** пользователя

### 10.2. Режимы системы

```
INITIALIZING → RUNNING → PAUSED → SHUTDOWN
                  │         ↑
                  │         │
                  └─────────┘
                  (при любой ошибке)
```

| Режим | Описание | Что разрешено |
|-------|----------|---------------|
| `INITIALIZING` | Загрузка моделей и данных | Ничего |
| `RUNNING` | Нормальная работа | Торговля |
| `PAUSED` | Ошибка, ожидание пользователя | Только мониторинг позиций |
| `SHUTDOWN` | Корректное завершение | Закрытие процессов |

### 10.3. Типы ошибок и реакции

| Ошибка | Действие | Алерт |
|--------|----------|-------|
| Биржа недоступна > 30 сек | PAUSED | CRITICAL |
| Модель не отвечает > 10 сек | Перезапуск модели | WARNING |
| Модель не отвечает > 60 сек | PAUSED | CRITICAL |
| Ошибка в risk manager | PAUSED | CRITICAL |
| Loss of internet | PAUSED | CRITICAL |
| Диск заполнен > 90% | Пауза записи | WARNING |
| Непредвиденная ошибка | PAUSED | CRITICAL |

## 13. 🚀 DEPLOYMENT И ОБНОВЛЕНИЯ

### 13.1. Обновление моделей

**Процесс:**
1. Обучение новой версии модели
2. Бэктест на out-of-sample данных
3. Регистрация в реестре
4. **Загрузка в "pending" состояние** (без остановки торговли)
5. Валидация на последних данных
6. **Автоматический swap**, если метрики лучше
7. Уведомление пользователя об обновлении

**Откат:** Мгновенный возврат к предыдущей версии через дашборд.

### 13.2. Запуск системы

```bash
# Запуск
python scripts/start_system.py

# Остановка (корректная)
python scripts/stop_system.py

# Проверка здоровья
python scripts/health_check.py

# Сбор данных
python scripts/collect_data.py --symbols BTC_USDT,ETH_USDT --timeframes 5m,1h,4h

# Обучение модели
```
