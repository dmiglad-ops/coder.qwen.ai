## 0. 📝 КОНТЕКСТ И ПРИНЦИПЫ

### 0.1. Ключевой принцип: СИГНАЛ ПЕРВЫЙ

> **Ни одна строка инфраструктуры не пишется до тех пор, пока не доказано, что сигнал существует и обыгрывает бенчмарк.**

Это означает:
- Сначала проверяем гипотезу на простых моделях (XGBoost/LightGBM)
- Только если альфа подтверждена — строим систему
- Если альфы нет — проект закрывается за 3-4 недели, а не за полгода
- Каждое решение о переходе на следующую фазу должно быть **обосновано данными**

### 0.2. Бенчмарки (ОБЯЗАТЕЛЬНЫ)

Каждая модель/стратегия **обязана** сравниваться с четырьмя бенчмарками:

| № | Бенчмарк | Что проверяет | Реализация |
|---|----------|---------------|------------|
| 1 | **Buy & Hold** | Есть ли альфа вообще | Купил в начале, продал в конце |
| 2 | **Случайные таймстампы** | Выбор МОМЕНТА входа | Случайные таймстампы, направление как у модели |
| 3 | **Перемешанные направления** | Выбор НАПРАВЛЕНИЯ | Таймстампы модели, случайное направление |
| 4 | **Простая стратегия** | Улучшение над наивным | Пересечение SMA 20/50 |

**ВАЖНО:** Бенчмарки №2 и №3 реализуются **по-разному**:
- №2: случайные таймстампы + направление в том же соотношении, что у модели → проверяет навык выбора момента
- №3: таймстампы модели + случайное направление → проверяет навык выбора направления

**Бенчмарк №4 сравнивается ПО SHARPE, не по абсолютной доходности.**

**Все метрики рассчитываются с учетом:**
- Комиссии: 0.1% (тейкер)
- Проскальзывание: 0.05% (параметризуется по паре)
- **Funding fees:** каждые 8 часов для перпетуалов

### 0.3. Ограничения железа

```
Железо:
├── CPU: Intel Xeon E5-2699v4 (22 ядра / 44 потока)
├── GPU: 2× NVIDIA GTX 1070 (8 GB каждая)
├── RAM: 32 GB DDR4
└── Storage: SSD

Ограничения:
├── Full fine-tune Laya 421M НЕВОЗМОЖЕН (нужно > 8 GB VRAM)
├── Решение: только LoRA/QLoRA или заморозка + обучение головы
├── Инференс в fp16: ~1 GB VRAM на модель (реалистично)
├── Максимум 2 модели по 421M на одну GPU одновременно
└── Директор: НЕ Laya 421M, а маленькая модель (MLP/GBM)
```

### 0.5. Источники данных (КРИТИЧНО)

**Явное разделение источников:**

| Назначение | Источник | Режим | Ключи |
|-----------|----------|-------|-------|
| Исторические данные | Bybit **MAINNET** REST API | Public | Не нужны |
| Реалтайм данные | Bybit **MAINNET** WebSocket | Public | Не нужны |
| Исполнение ордеров | Bybit **TESTNET** REST API | Demo | Нужны |
| Позиции и балансы | Bybit **TESTNET** REST API | Demo | Нужны |
| Исторические funding rates | Bybit **MAINNET** API | Public | Не нужны |

**Почему такое разделение:**
- На TESTNET цены могут расходиться с MAINNET в моменты волатильности
- Модель обучается на MAINNET-данных, значит и реалтайм должен быть с MAINNET
- На TESTNET отправляем только ордера (демо-режим)
- Расхождение > 0.5% между MAINNET и TESTNET → алерт WARNING

**Маппинг символов:**

| Внутренний | ccxt | Bybit API | Отображение | Комиссия | Проскальзывание |
|-----------|------|-----------|-------------|----------|-----------------|
| `SOL_USDT` | `SOL/USDT` | `SOLUSDT` | SOL/USDT | 0.1% | 0.05% |
| `BTC_USDT` | `BTC/USDT` | `BTCUSDT` | BTC/USDT | 0.1% | 0.03% |
| `ETH_USDT` | `ETH/USDT` | `ETHUSDT` | ETH/USDT | 0.1% | 0.03% |

**Примечание:** Комиссии указаны консервативно (реально на Bybit тейкер ~0.055%). Проскальзывание параметризуется для каждой пары отдельно и пересматривается при добавлении каждой новой пары.

### 1.3. Ключевые решения

| Решение | Выбор | Обоснование |
|---------|-------|-------------|
| Оркестрация | **asyncio** (Phase 0-2), **asyncio + multiprocessing** (Phase 3+) | ZeroMQ на старте = лишняя сложность |
| Модель | **Сначала дерево** (XGBoost), потом (если нужно) трансформер | Проверка гипотезы без риска |
| Директор | **Маленький MLP или rule-based**, НЕ Laya | Laya на CPU для 10 пар = слишком медленно |
| Данные | **Mainnet** для обучения/реалтайма, **Testnet** для исполнения | На testnet нет полной истории и цены расходятся |
| Батчинг | **Обязателен** с Phase 3 | Один вызов модели на все пары вместо 40 |
| Свечи | **Только закрытые** | Незакрытая свеча = будущая информация |
| Веб-дашборд | **С Phase 2**, не раньше | Для фаз 0-1 достаточно HTML отчета |
| Позиции | **Максимум 1 на пару** | Корректность статистики |
| Вход | **Симметричный** (лонг + шорт) | Избегаем фандинга на лонг-онли |

### 1.4. Защита позиций (КРИТИЧНО)

**Принцип:** Позиции защищены на уровне биржи, даже если процесс упал.

```
EXCHANGE-NATIVE стопы (ставятся ВСЕГДА на бирже):
├── Stop-loss: ATR-based (определяется на валидации)
├── Take-profit: ATR-based (определяется на валидации)
└── Цель: защита позиции при падении процесса

ПРОЦЕСС системы (режим RUNNING):
├── Открывает позиции
├── Мониторит через reconciliation
└── Может закрыть по доп. условиям (см. раздел 10.1)

РЕЖИМ PAUSED:
├── НЕ открывает новые позиции
├── НЕ вмешивается в существующие (ручное закрытие через биржу)
├── Продолжает reconciliation (чтобы видеть, что закрылось по стопу)
└── Ждет ручного вмешательства

АВАРИЙНЫЙ РЕЖИМ (только при явной настройке):
├── Настраивается в конфиге:
│   └── emergency_close_on_unavailable: false (по умолчанию)
├── Если включено: при недоступности > 10 мин → попытка закрыть
└── Только через отдельный канал (резервный API)

НИКОГДА:
├── НЕ закрывать позиции автоматически без настройки
├── НЕ закрывать позиции при обычной паузе
└── НЕ принимать решений за пользователя
```

**Конфигурация:**
```yaml
# config/risk.yaml
emergency:
  close_on_exchange_unavailable: false  # По умолчанию отключено
  unavailable_timeout_minutes: 10       # Через сколько минут считать недоступной
  backup_api_enabled: false             # Резервный канал для аварийного закрытия
```

```python
def generate_labels(df, forward_period=24, atr_period=14):
    """
    Генерация меток с учетом волатильности.
    
    Порог: 2 × ATR (адаптивный, не фиксированный).
    
    Метки:
    - 1 (long): цена через 24 свечи > текущая + 2×ATR
    - -1 (short): цена через 24 свечи < текущая - 2×ATR
    - 0 (hold): всё остальное
    
    ВАЖНО: проверяем дисбаланс классов и корректируем.
    """
    # Расчет ATR
    atr = calculate_atr(df, period=atr_period)
    
    # Будущая цена
    future_price = df["close"].shift(-forward_period)
    
    # Пороги на основе волатильности
    threshold = 2 * atr
    
    # Генерация меток
    labels = pd.Series(0, index=df.index)  # По умолчанию hold
    labels[future_price > df["close"] + threshold] = 1    # long
    labels[future_price < df["close"] - threshold] = -1   # short
    
    # Проверка дисбаланса
    class_counts = labels.value_counts(normalize=True)
    print("Распределение классов:")
    print(class_counts)
    
    # Если hold > 70%, нужно скорректировать
    if class_counts.get(0, 0) > 0.70:
        print("ВНИМАНИЕ: сильный дисбаланс классов")
        print("Варианты решения:")
        print("1. Использовать sample_weight (для мультикласса)")
        print("2. Перейти на бинарную задачу (long vs not-long)")
        print("3. Снизить порог до 1.5×ATR")
    
    return labels, class_counts
```

### 3.6. Модель

```python
# Phase 0 модель: XGBoost (НЕ Laya!)

import xgboost as xgb
from sklearn.utils.class_weight import compute_class_weight
import numpy as np


def create_model_with_class_weights(X_train, y_train, X_val, y_val):
    """
    Создание модели с корректировкой дисбаланса классов.
    
    ВАЖНО: Для мультикласса используем sample_weight, а не scale_pos_weight!
    scale_pos_weight — это скаляр только для бинарной классификации.
    """
    # Вычисляем веса классов
    classes = np.unique(y_train)
    class_weights = compute_class_weight(
        "balanced", 
        classes=classes, 
        y=y_train
    )
    
    # Создаем веса для каждого образца
    sample_weights = class_weights[np.searchsorted(classes, y_train)]
    
    # Модель
    model = xgb.XGBClassifier(
        n_estimators=500,
        max_depth=6,
        learning_rate=0.05,
        subsample=0.8,
        colsample_bytree=0.8,
        reg_alpha=0.1,
        reg_lambda=1.0,
        random_state=42,
        eval_metric="mlogloss",
        early_stopping_rounds=50,
    )
    
    # Обучение с весами
    model.fit(
        X_train, y_train,
        sample_weight=sample_weights,
        eval_set=[(X_val, y_val)],
        verbose=True
    )
    
    return model
```

```python
import optuna


def optimize_xgboost(X_train, y_train, X_val, y_val, n_trials=100):
    """
    Подбор гиперпараметров через Optuna.
    
    Метрика: Sharpe на валидации.
    
    ВАЖНО: На OOS не смотрим никогда, даже для выбора метрики.
    
    ПРИМЕЧАНИЕ: Для дисбаланса классов используем sample_weight.
    """
    # Вычисляем веса классов
    classes = np.unique(y_train)
    class_weights = compute_class_weight("balanced", classes=classes, y=y_train)
    sample_weights = class_weights[np.searchsorted(classes, y_train)]
    
    def objective(trial):
        params = {
            "n_estimators": trial.suggest_int("n_estimators", 100, 1000),
            "max_depth": trial.suggest_int("max_depth", 3, 8),
            "learning_rate": trial.suggest_float("learning_rate", 0.01, 0.3, log=True),
            "subsample": trial.suggest_float("subsample", 0.6, 1.0),
            "colsample_bytree": trial.suggest_float("colsample_bytree", 0.6, 1.0),
            "reg_alpha": trial.suggest_float("reg_alpha", 1e-8, 10.0, log=True),
            "reg_lambda": trial.suggest_float("reg_lambda", 1e-8, 10.0, log=True),
            "min_child_weight": trial.suggest_int("min_child_weight", 1, 10),
        }
        
        model = xgb.XGBClassifier(
            **params, 
            eval_metric="mlogloss",
            early_stopping_rounds=50
        )
        model.fit(
            X_train, y_train,
            sample_weight=sample_weights,
            eval_set=[(X_val, y_val)],
            verbose=False
        )
        
        # Метрика: Sharpe на валидации
        sharpe = calculate_sharpe_from_predictions(model, X_val, y_val)
        return sharpe
    
    study = optuna.create_study(direction="maximize")
    study.optimize(objective, n_trials=n_trials, show_progress_bar=True)
    
    return study.best_params, study.best_value
```

```python
def walk_forward_validation(data, model_class, n_splits=5, embargo=72):
    """
    Walk-forward валидация с embargo.
    
    ВАЖНО: embargo должен покрывать МАКСИМАЛЬНЫЙ период удержания позиции!
    Не только label horizon (24 свечи), но и exit policy (48ч = 48 свечей)
    
    embargo = max(forward_period, max_holding_period) + запас
    При time-based exit 48ч и 1h-свечах: минимум 50 баров
    Используем 72 бара (3 дня) с запасом
    """
    results = []
    
    tscv = TimeSeriesSplit(n_splits=n_splits)
    
    for fold, (train_idx, test_idx) in enumerate(tscv.split(data)):
        # Применяем embargo
        train_idx = train_idx[:-embargo]
        
        if len(train_idx) == 0:
            continue

        y_train = data.iloc[train_idx]["label"]
```

### 3.9. Бэктест с учётом перекрытия (КРИТИЧНО)

```
═══════════════════════════════════════════════════════════════════
           БЭКТЕСТ С УЧЁТОМ ПЕРЕКРЫТИЯ СДЕЛОК
═══════════════════════════════════════════════════════════════════

ПРОБЛЕМА:
- Метки смотрят на 24 свечи вперёд
- Соседние метки перекрываются на 23 часа
- Соседние "сделки" в симуляции тоже перекрываются
- t-статистика без поправки завышается в разы
- Эффективный размер выборки может быть в 5 раз меньше заявленного

РЕШЕНИЕ (основное): Non-overlapping backtest

В симуляции ЗАПРЕЩАТЬ вход, пока предыдущая позиция не закрыта.
Это соответствует правилу "1 позиция на пару".

Реальный N сделок = 100-200 за 20 месяцев (не 300+).
Тогда t-статистика считается корректно.

РЕШЕНИЕ (дополнительное): Block bootstrap

Оценивать значимость через bootstrap по блокам длиной ≥ forward_period.

def block_bootstrap_significance(trade_returns, block_size=24, n_bootstrap=1000):
    """
    Block bootstrap для корректной оценки значимости.
    """
    n_blocks = len(trade_returns) // block_size
    bootstrapped_means = []
    
    for _ in range(n_bootstrap):
        # Случайные блоки
        block_indices = np.random.choice(n_blocks, size=n_blocks, replace=True)
        
        # Собираем выборку из блоков
        bootstrap_sample = []
        for block_idx in block_indices:
            start = block_idx * block_size
            end = start + block_size
            bootstrap_sample.extend(trade_returns[start:end])
        
        bootstrapped_means.append(np.mean(bootstrap_sample))
    
    # p-value: доля бутстрапов с средним <= 0
    p_value = np.mean(np.array(bootstrapped_means) <= 0)
    
    return {
        "mean": np.mean(trade_returns),
        "p_value": p_value,
        "ci_95": np.percentile(bootstrapped_means, [2.5, 97.5])
    }

РЕШЕНИЕ (альтернативное): Newey-West standard errors
```

```python
def run_benchmarks_corrected(model, X_test, y_test, timestamps, n_runs=1000):
    """
    ПРАВИЛЬНАЯ реализация бенчмарков.
    
    Разделяем навыки:
    - Бенчмарк 2: проверяет выбор МОМЕНТА
    - Бенчмарк 3: проверяет выбор НАПРАВЛЕНИЯ
    - Бенчмарк 4: сравниваем ПО SHARPE, не по абсолютной доходности
    """
    # Получаем предсказания модели
    model_predictions = model.predict(X_test)
    model_probabilities = model.predict_proba(X_test)
    model_timestamps = timestamps[model_predictions != 0]
    
    # ────────────────────────────────────────────────────────────
    # БЕНЧМАРК 1: Buy & Hold
    # ────────────────────────────────────────────────────────────
    buyhold = simulate_buyhold(X_test, timestamps)
    
    # ────────────────────────────────────────────────────────────
    # БЕНЧМАРК 2: Случайные таймстампы, направление как у модели
    # ────────────────────────────────────────────────────────────
    # Проверяет: умеет ли модель выбирать МОМЕНТ входа?
    
    active_predictions = model_predictions[model_predictions != 0]
    long_ratio = (active_predictions == 1).sum() / len(active_predictions)
    
    random_timestamp_results = []
    for _ in range(n_runs):
        random_indices = np.random.choice(len(X_test), size=len(model_timestamps), replace=False)
        random_directions = np.where(
            np.random.random(len(random_indices)) < long_ratio,
            1, -1
        )
        
        random_labels = np.zeros(len(X_test))
        random_labels[random_indices] = random_directions
        
        pnl = simulate_trading(random_labels, timestamps)
        random_timestamp_results.append(pnl)
    
    benchmark_2 = np.array(random_timestamp_results)
    
    # ────────────────────────────────────────────────────────────
    # БЕНЧМАРК 3: Таймстампы модели, случайное направление
    # ────────────────────────────────────────────────────────────
    # Проверяет: умеет ли модель выбирать НАПРАВЛЕНИЕ?
    
    shuffled_direction_results = []
    for _ in range(n_runs):
        shuffled_labels = np.zeros(len(X_test))
        shuffled_labels[model_timestamps] = np.random.choice(
            [1, -1], size=len(model_timestamps)
        )
        
        pnl = simulate_trading(shuffled_labels, timestamps)
        shuffled_direction_results.append(pnl)
    
    benchmark_3 = np.array(shuffled_direction_results)
    
    # ────────────────────────────────────────────────────────────
    # БЕНЧМАРК 4: Простая стратегия
    # ────────────────────────────────────────────────────────────
    # ВАЖНО: сравниваем ПО SHARPE, не по абсолютной доходности!
    
    sma_strategy = simulate_sma_cross(X_test, timestamps)
    benchmark_4 = {
        "total_return": sma_strategy["total_return"],
        "sharpe": sma_strategy["sharpe"],
        "max_drawdown": sma_strategy["max_drawdown"],
        "model_better_by_sharpe": model_sharpe > sma_strategy["sharpe"],
    }
    
    # ────────────────────────────────────────────────────────────
    # РЕЗУЛЬТАТЫ
    # ────────────────────────────────────────────────────────────
    
    model_pnl = simulate_trading(model_predictions, timestamps)
    
    return {
        "model_pnl": model_pnl,
        
        "buyhold": buyhold,
        
        "benchmark_2_timing": {
            "mean": benchmark_2.mean(),
            "std": benchmark_2.std(),
            "model_percentile": (benchmark_2 < model_pnl).mean() * 100,
            "passes": (benchmark_2 < model_pnl).mean() > 0.95
        },
        
        "benchmark_3_direction": {
            "mean": benchmark_3.mean(),
            "std": benchmark_3.std(),
            "model_percentile": (benchmark_3 < model_pnl).mean() * 100,
            "passes": (benchmark_3 < model_pnl).mean() > 0.95
        },
        
        "benchmark_4_sma": benchmark_4,
        
        "interpretation": interpret_benchmarks(benchmark_2, benchmark_3, model_pnl)
    }


def interpret_benchmarks(benchmark_2, benchmark_3, model_pnl):
    """
    Интерпретация результатов бенчмарков.
    """
    passes_timing = (benchmark_2 < model_pnl).mean() > 0.95
    passes_direction = (benchmark_3 < model_pnl).mean() > 0.95
    
    if passes_timing and passes_direction:
        return "FULL ALPHA: модель умеет и момент, и направление"
    elif passes_timing and not passes_direction:
        return "TIMING ONLY: модель выбирает момент, но не направление"
    elif not passes_timing and passes_direction:
        return "DIRECTION ONLY: модель выбирает направление, но не момент"
    else:
        return "NO ALPHA: модель не лучше случайности"
```

```
✅ ГО (продолжаем проект), если ВСЕ условия выполнены:

1. Риск-скорректированная доходность:

   - Если сделок ≥ 300: достаточно t-статистики > 2.0
   - t-статистика считается с поправкой на автокорреляцию

   - p-value < 0.05

   - Модель в топ-5% распределения случайных таймстампов (№2)

     (не по абсолютной доходности)
   - Интерпретация: "FULL ALPHA" или хотя бы "TIMING + DIRECTION"

4. Устойчивость:
   - Все фолды walk-forward имеют положительный результат

   - Коэффициент вариации фолдов < 0.5:

   - Знак зависимости НЕ скачет между фолдами
   - В фичах НЕ обнаружен look-ahead

- Одна фича даёт > 90% вклада в предсказание
- Обнаружен look-ahead в SHAP анализе
- Модель лучше только одного бенчмарка из трёх

- Одна фича даёт 50-90% вклада → исследовать, но не закрывать
```

### 4.2. Правильный мульти-ТФ без look-ahead (КРИТИЧНО)

```python
def merge_multitimeframe_correctly(df_1h, df_4h):
    """
    ПРАВИЛЬНОЕ объединение мульти-таймфреймовых данных.
    
    КРИТИЧНО: используем merge_asof с direction="backward",
    чтобы избежать look-ahead.
    """
    # Вычисляем время закрытия 4h свечи
    df_4h["close_time"] = df_4h["timestamp"] + 4 * 3600 * 1000  # ms
    
    # Для каждой 1h свечи берём последнюю ЗАКРЫТУЮ 4h свечу
    # Это происходит ДО момента времени 1h свечи
    df_merged = pd.merge_asof(
        df_1h.sort_values("timestamp"),
        df_4h[["close_time", "ema_20", "ema_50", "atr_14", "adx"]].sort_values("close_time"),
        left_on="timestamp",
        right_on="close_time",
        direction="backward"  # Только закрытые свечи!
    )
    
    # Переименовываем колонки для ясности
    df_merged = df_merged.rename(columns={
        "ema_20": "ema_20_4h",
        "ema_50": "ema_50_4h",
        "atr_14": "atr_14_4h",
        "adx": "adx_4h"
    })
    
    return df_merged
```

### 4.5. Порог уверенности (по PR-кривой)

```python
def find_optimal_threshold(y_val, y_prob, method="expected_value"):
    """
    Подбор оптимального порога по PR-кривой.
    
    НЕ берем фиксированное значение с потолка!
    """
    thresholds = np.linspace(0.5, 0.9, 20)
    best_threshold = 0.5
    best_score = -np.inf
    
    for threshold in thresholds:
        y_pred = (y_prob >= threshold).astype(int)
        
        if y_pred.sum() < 10:
            continue
        
        # Expected value per trade
        wins = (y_pred == 1) & (y_val == 1)
        losses = (y_pred == 1) & (y_val == 0)
        
        if wins.sum() == 0 or losses.sum() == 0:
            continue
        
        p_win = wins.sum() / y_pred.sum()
        
        # Expected value: P(win) × avg_win - P(loss) × avg_loss
        ev = p_win * 1.0 - (1 - p_win) * 1.0  # normalized
        
        if ev > best_score:
            best_score = ev
            best_threshold = threshold
    
    return best_threshold, best_score
```

```python
def optimize_stops(X_train, y_train, X_val, y_val, n_trials=50):
    """
    Подбор ATR-based стопов через grid search.
    
    ВАЖНО: Согласованность меток и стопов!
    
    Проблема:
    - Метки: 2×ATR-барьер за 24 часа
    - Выход: SL/TP/48 часов
    - Это разные правила выхода
    
    Решение:
    - При подборе SL/TP проверяем согласованность
    - Если оптимизированные стопы меняют исходы против меток →
      переразмечаем под реальный экзит
    """
    best_params = None
    best_sharpe = -np.inf
    
    k_values = [1.5, 2.0, 2.5, 3.0]
    m_values = [2.0, 3.0, 4.0, 5.0]
    
    for k in k_values:
        for m in m_values:
            # Обучаем модель с этими параметрами
            model = train_model_with_stops(X_train, y_train, sl_k=k, tp_m=m)
            
            # Оцениваем на валидации
            sharpe = evaluate_sharpe(model, X_val, y_val, sl_k=k, tp_m=m)
            
            if sharpe > best_sharpe:
                best_sharpe = sharpe
                best_params = {"sl_k": k, "tp_m": m}
    
    # Проверяем согласованность
    check_label_stop_consistency(X_val, y_val, best_params)
    
    return best_params, best_sharpe
```

### 4.7. Exit Policy

```python
class ExitPolicy:
    """
    Политика выхода из позиции (в дополнение к биржевым стопам).
    """
    
    def check_exit(self, position, current_data, model_signal):
        """
        Проверка дополнительных условий выхода.
        """
        # 1. Time-based: закрыть через 48ч если нет TP
        if hours_since_entry(position) > 48:
            return "time_exit"
        
        # 2. Signal reversal: сигнал развернулся
        if position.side == "long" and model_signal["P(long)"] < 0.4:
            return "signal_reversal"
        
        if position.side == "short" and model_signal["P(short)"] < 0.4:
            return "signal_reversal"
        
        # 3. Stagnation: нет движения > 24ч
        if abs(position.unrealized_pnl_pct) < 0.005 and hours_since_entry(position) > 24:
            return "stagnation"
        
        return None
```

### 5.2. Позиционный размер

```
ПОЗИЦИОННЫЙ РАЗМЕР (для фазы 2):

Базовый метод: Volatility-adjusted

Формула:
  position_size = base_size × (target_volatility / current_atr_pct)

Где:
  base_size = 3% (базовый размер позиции)
  target_volatility = 2% (целевая волатильность)
  current_atr_pct = ATR_14 / close × 100 (текущая волатильность в %)

Ограничения:
  Минимальный размер: 1%
  Максимальный размер: 5%

Пример:
  Если ATR = 3$ при цене 150$ → волатильность 2%
  → размер = 3% × (2% / 2%) = 3%
  
  Если ATR = 4.5$ при цене 150$ → волатильность 3%
  → размер = 3% × (2% / 3%) = 2%
  
  Если ATR = 1.5$ при цене 150$ → волатильность 1%
  → размер = 3% × (2% / 1%) = 6% (но максимум 5%)

ПРАВИЛО: Максимум 1 открытая позиция на пару.
```

```
│  • Позиции НЕ закрываются (биржевые стопы остаются активны)      │
│  • Новые сделки НЕ открываются                                   │
│  • Продолжается периодическая сверка (каждые 5 минут)            │
│  • Отправлен алерт в МАКС                                        │
│  • Ожидание ручного вмешательства                                │
│  • Переход: → RUNNING (после исправления), → SHUTDOWN            │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  SHUTDOWN                                                        │
│  • Корректное завершение всех процессов                          │
│  • Сохранение итогового checkpoint                               │
│  • Финальная сверка с биржей                                     │
│  • Закрытие всех соединений                                      │
│  • Логирование завершения                                        │
└──────────────────────────────────────────────────────────────────┘
```

### 9.3. Матрица ошибок

| Ошибка | Действие | Алерт | Режим |
|--------|----------|-------|-------|
| Биржа недоступна > 30 сек | Пауза торговли | WARNING | PAUSED |
| Биржа недоступна > 5 мин | Пауза + сверка | CRITICAL | PAUSED |
| Модель не отвечает > 10 сек | Перезапуск модели | WARNING | RUNNING |
| Модель не отвечает > 60 сек | Пауза | CRITICAL | PAUSED |
| Расхождение цен > 0.5% | Пауза торговли | WARNING | PAUSED |
| Дневной лимит убытков достигнут | Пауза торговли | CRITICAL | PAUSED |
| Непредвиденная ошибка | Пауза + логирование | CRITICAL | PAUSED |

**Примечание:** "Закрытие позиций" при недоступности биржи **НЕ выполняется** по умолчанию. Только если явно включено в конфиге (см. раздел 1.4).

### 9.5. Периодическая сверка

```python
class PositionTracker:
    def __init__(self):
        self.last_sync_time = None
        self.sync_interval = 3600  # Каждый час
    
    async def maybe_sync(self, executor):
        """
        Периодическая синхронизация с биржей.
        """
        now = datetime.now()
        
        if self.last_sync_time is None or \
           (now - self.last_sync_time).seconds > self.sync_interval:
            
            exchange_positions = await executor.get_open_positions()
            self.reconcile(exchange_positions)
            self.last_sync_time = now
    
    def reconcile(self, exchange_positions):
        """
        Синхронизация локального состояния с биржей.
        """
        # Позиции на бирже, которых нет локально
        for ep in exchange_positions:
            if ep.id not in self.local_positions:
                logger.warning(f"Найдена позиция на бирже: {ep}")
                self.local_positions[ep.id] = ep
        
        # Локальные позиции, которых нет на бирже
        for lp_id, lp in list(self.local_positions.items()):
            if lp_id not in [ep.id for ep in exchange_positions]:
                logger.info(f"Позиция закрылась (возможно по стопу): {lp}")
                self.close_trade(lp_id, reason="closed_on_exchange")
                del self.local_positions[lp_id]
```

## 10. 📋 ДОПОЛНИТЕЛЬНЫЕ ПОЛИТИКИ

### 10.1. Exit Policy

```
Условия выхода из позиции (в дополнение к биржевым стопам):

1. Time-based:
   └── Закрыть через 48 часов, если не сработал TP
   └── Цель: не держать позиции в застое

2. Signal reversal:
   └── Закрыть, если сигнал развернулся
   └── Для long: P(long) < 0.4 → закрыть
   └── Для short: P(short) < 0.4 → закрыть

3. Stagnation:
   └── Закрыть, если нет движения > 24 часа
   └── Если |PnL| < 0.5% за 24ч → закрыть

4. Частичный TP (опционально):
   └── При достижении 50% TP закрыть половину позиции
   └── Остаток держать до полного TP
```

### 10.2. Retraining Policy

```
Политика переобучения:

Частота: раз в 8-12 недель (не 4!)

Обоснование:
- При 30-месячном окне новые 4 недели = 0.3% данных
- Модель почти не изменится
- Затраты на retrain + калибровку + shadow — реальные

Train window: rolling last 30 месяцев
OOS window: последние 3 месяца (которых не было в train)

Триггеры для внепланового переобучения:
1. Дрейф данных: KL-дивергенция > порога
2. Live Sharpe упал ниже backtest Sharpe на 30%+
3. Калибровка деградировала: ECE > 0.10

Процесс:
1. Обучить новую версию на актуальных данных
2. Калибровка на валидации (3 месяца)
3. Если лучше текущей → SHADOW MODE (6-8 недель, не 1-2!)
   ├── Новая модель считает решения параллельно
   ├── НЕ торгует, только логирует
   └── Сравниваем с реальной моделью
4. Если shadow результаты лучше → PROMOTE в prod
5. Если хуже → DISCARD

ВАЖНО:
- Shadow минимум 6-8 недель для осмысленного сравнения
- Если сделок < 30 → продлить до набора
- Параллельно логировать ВСЕ сигналы (не только выше порога)
```

### 10.3. Пере-калибровка

```
ПЕРЕ-КАЛИБРОВКА:

Частота: раз в 8 недель или при триггерах

ВАЖНО: Пере-калибровка должна быть согласована с retraining!

Если калибровка обновляется чаще модели:
- Используем один и тот же валидационный набор всё чаще
- Это может привести к переобучению калибровки

Решение:
- Калибруем только при retraining (раз в 8-12 недель)
- ИЛИ используем отдельный валидационный набор для калибровки
- НЕ используем OOS данные для калибровки

Триггеры для внеплановой пере-калибровки:
1. ECE (Expected Calibration Error) > 0.10 на последних 100 сделках
2. Дрейф данных: z-score любой фичи > 3.0
3. Разница между предсказанной и реальной частотой событий > 15%
```

### 10.4. Funding Fees

```
Учет funding в бэктесте и в живой торговле:

Формула:
funding_cost = position_value × funding_rate × (holding_hours / 8)

Исторические данные:
└── Bybit API /v5/market/funding/history
└── Пагинация: ~200 записей за запрос
└── С 2022 года: ~9-10 запросов на пару

В бэктесте:
├── Для каждой позиции считаем количество выплат
├── Учитываем знак (лонг платит при положительном рейте)
└── Вычитаем из PnL

В живой торговле:
├── Мониторим текущий funding
├── При приближении времени выплаты → учитываем
└── Включаем в итоговый PnL

ВАЖНО:
- Используем ИСТОРИЧЕСКИЙ funding на момент удержания позиции
- НЕ текущий (иначе искажение)
```

### 10.6. Data Drift Monitoring

```
Мониторинг дрейфа данных:

Что мониторим:
├── Средние/дисперсии фичей в проде vs трейне
├── Для bounded фичей (RSI, CCI): используем MAD вместо z-score
├── Для тяжелохвостых фичей: Mann-Whitney U тест
└── Регулярно (раз в неделю) считаем live Sharpe vs backtest

Алгоритм:
1. Собираем статистику фичей из трейна:
   {
     'feature_name': {'mean': x, 'std': y, 'min': a, 'max': b}
   }

2. В проде для каждой фичи считаем отклонение:
   - Для bounded: MAD-based z-score
   - Для остальных: обычный z-score

3. Если отклонение > 3.0 → WARNING алерт
4. Если отклонение > 5.0 → CRITICAL алерт + пауза торговли

Частота проверки: каждый час
```
